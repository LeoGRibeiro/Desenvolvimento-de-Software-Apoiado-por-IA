# Experimento Prático: Decomposição de Tarefas e Correção de Bugs em Open Source (Zod)

**Contexto e Objetivo:** Como parte das atividades práticas do diário acadêmico da disciplina de Desenvolvimento de Software Apoiado por IA, o objetivo deste experimento foi avaliar a capacidade de LLMs na resolução de bugs arquiteturais complexos em projetos open source reais com sistemas de tipos avançados. Isolamos uma regressão crítica do Zod v4 (referente à PR #6530 / Issue #6526), na qual esquemas recursivos construídos por funções de fábrica disparavam estouro de pilha (`RangeError: Maximum call stack size exceeded`) durante a detecção de ciclos no `memoizer` e nas operações de derivação de objetos. O experimento foi executado em ambiente duplo-cego (sem histórico do Git e sem acesso à solução prévia), avaliando empiricamente como a engenharia de contexto — combinando restrições estritas de engenharia (`AGENTS.md`) e planejamento estruturado prévio (`NOTES.md`) — possibilita a resolução "às cegas" e de primeira tentativa, comparando-a criticamente com a solução oficial humana mergeada no repositório.

## O que foi feito:

- **Seleção e Setup:** O repositório do Zod (v4) foi preparado em ambiente duplo-cego, removendo o histórico de commits do Git e injetando exclusivamente a suíte de testes de regressão (`cyclic-data.test.ts` e `object.test.ts`) como oráculo de validação.
- **Engenharia de Contexto e Execução:** Em vez de realizar tentativas cegas de codificação direta, o processo foi desacoplado em duas etapas: elaboração de um plano arquitetural estruturado no `NOTES.md` (mapeando a raiz do estouro de pilha em getters não resolvidos e clonagens ingênuas com object spread) e execução rigorosamente restrita pelo `AGENTS.md` (tipagem TypeScript estrita, sem console.logs, comentários concisos e sem ramificação por tipo de schema em código compartilhado). A IA corrigiu os 5 arquivos necessários em uma única iteração de ~15 minutos, alcançando 100% de aprovação (393/393 testes) sem regressões ou lints quebrados.
- **Análise Comparativa:** Utilizou-se navegação web autônoma via protocolo MCP (Puppeteer) para inspecionar a PR original #6530 no GitHub, comparando a descrição técnica, as decisões de baixo nível e os diffs dos mantenedores humanos contra o código gerado pela IA.

## Diferença entre as implementações:

### Solução Oficial (Humana - Mergeada no repositório):
A solução dos mantenedores do Zod focou em micro-otimizações de runtime e de alocação de memória no motor V8. Para evitar criar estruturas laterais, anexaram o shape bruto diretamente ao próprio objeto da função do getter (`get.raw = sh`) através de uma interface de extensão (`ShapeGetter`). Na detecção de ciclos, implementaram uma máquina de estados tri-state (`NONE = 0`, `ASSUMED = 1`, `PROVEN = 2`) controlada por uma flag booleana `resolve` que desativa o aprofundamento recursivo em nós `z.lazy`. Nos builders de objetos (`pick`, `omit`, `extend`, etc.), para poupar até 23% de custo de CPU em relação ao uso generalizado de `Object.defineProperty`, criaram uma função de escrita condicional `putProp` que prefere atribuição direta e só usa `defineProperty` caso a chave já exista no alvo. Substituíram os clones com spread `{ ...def }` por `util.mergeDefs`.

```typescript
// Solução Oficial Humana (PR #6530)
// Em schemas.ts: anotação direta na própria função getter
export interface ShapeGetter {
  (): Record<PropertyKey, any>;
  raw: Record<PropertyKey, any>;
}

const get: util.ShapeGetter = () => {
  const newSh = { ...sh };
  Object.defineProperty(def, "shape", { value: newSh });
  get.raw = newSh;
  return newSh;
};
get.raw = sh;
Object.defineProperty(def, "shape", { get });

// Em util.ts: escrita otimizada para evitar overhead de defineProperty
function putProp(target: any, key: PropertyKey, value: any): void {
  if (key in target) assignProp(target, key as any, value);
  else target[key] = value;
}
```

### Solução Gerada no Experimento (LLM):
A IA, estritamente orientada pelas diretrizes de clean code e invariantes de tipos do `AGENTS.md`, priorizou segurança de tipagem e desacoplamento de estado. Em vez de mutar a função getter em runtime com propriedades dinâmicas, utilizou uma tabela fraca lateral (`util.propShapes = new WeakMap()`), preservando a assinatura funcional pura do JavaScript. Na detecção de ciclos no memoizer, derivou de forma independente uma máquina tri-state idêntica (`EXACT_FINITE = 0`, `EXACT_CYCLE = 1`, `DEFERRED_CYCLE = 2`), limitando a profundidade de `z.lazy` através de um contador de saltos (`lazyHops`). Nos builders de objetos, implementou validação síncrona imediata das chaves (`assertDeclaredKeys`), proteção contra poluição de protótipo (checando `hasOwnProperty` para evitar a armadilha de `__proto__` resolvendo para `Object.prototype`) e getters auto-cacheados (*self-caching accessors*) sob demanda. Assim como a solução humana, eliminou os spreads ingênuos de `def` via `util.mergeDefs`.

```typescript
// Solução Gerada pela LLM no Experimento
// Em util.ts & schemas.ts: desacoplamento de metadados via WeakMap
export const propShapes: WeakMap<object, Record<PropertyKey, any>> = new WeakMap();

// Em util.ts: builders derivam shapes com getters auto-cacheados sob demanda
Object.defineProperty(newShape, key, {
  get(this: any) {
    const val = (schema._zod.def.shape as any)[key];
    const result = wrap ? wrap(val, key) : val;
    Object.defineProperty(this, key, { value: result, writable: true, enumerable: true, configurable: true });
    return result;
  },
  enumerable: true,
  configurable: true,
});

// Em util.ts: validação síncrona com proteção contra propriedades de protótipo
for (const key of Reflect.ownKeys(mask)) {
  if (!Object.prototype.propertyIsEnumerable.call(raw, key)) {
    throw new Error(`Unrecognized key: "${String(key)}"`);
  }
}
```

## Resultado e Conclusão do Experimento:
Ambas as abordagens convergiram com precisão cirúrgica no diagnóstico central: a necessidade de um modelo de certeza de 3 estados (não armazenando ciclos presumidos em cache definitivo para permitir re-avaliação pós-parse) e o fim do spread em definições de schemas. Enquanto os desenvolvedores humanos priorizaram micro-otimizações mecânicas no V8 (anotações de funções e redução de chamadas a `defineProperty`), a LLM concebeu uma solução mais fortemente desacoplada (via `WeakMap`) e com garantias robustas de tipagem. Este resultado comprova empiricamente a hipótese de que o uso combinado de **decomposição prévia de tarefas** (`NOTES.md`) e **restrições explícitas de arquitetura e sistema** (`AGENTS.md`) elimina a necessidade de tentativa e erro, permitindo ao LLM resolver problemas arquiteturais de ponta em projetos open source complexos de forma limpa, segura e na primeira iteração.
